# dsh-systray · 恢复取消按钮状态 + 导入插件无条件添加（先激活、不兼容再禁用）评估

日期：2026-09-05 · 基于已实施（未提交）的 v0.7.1 代码基线。

---

## 需求 1：点击「取消恢复」后，取消未完成期间保持按钮禁用

**现状（已核实）**：`frontend/dist/main.js` wireImport 中取消监听为——
点击 → `CancelRestore()` → `btn-imp-cancel.disabled = true` → 文案「正在取消，即将回退…」
→ **3 秒定时器重新启用**（L946）；`import:done` 到达后才隐藏并复位（L1006-1007）。
问题：取消若超过 3 秒（7z 杀进程 / pnpm 对齐中途 / 回退重启），3 秒后按钮恢复可点，
与"取消未完成即应禁用"的要求不符。

**步骤（改动很小）**
1. 删除 L946 的 3 秒重新启用定时器；点击后保持 `disabled` 直到 `import:done` 到达
   （done 处理器已有 `disabled=false` + `classList.add("hidden")` 复位，无需新增逻辑）。
2. （加固，建议）`ui:show-settings` 重开窗口时按后端真实状态恢复忙碌 UI：
   若恢复任务仍在后台运行而窗口期间被隐藏/关闭，前端状态丢失会导致「恢复」按钮可点、
   取消按钮不可见。方案：新增绑定 `GetRestoreState() {running bool, kind string}`
   （读 `importJob`），`renderImportRows`/窗口重开时若 running 则 `setImportBusy(true)` 并
   显示取消按钮与进度区。若不做此项，需在文档注明窗口重开场景的已知缺口。

**关键问题点**
- Go 侧 `CancelRestore` 已幂等（atomic 标志），双击不会产生副作用；本需求纯前端状态问题。
- 「取消中」是单向状态：一旦点击，直到 `import:done`（canceled/ok/error 任一）才复位；
  若取消请求太晚（任务已完成），done=ok 正常收尾，按钮随进度区隐藏，无歧义。
- 窗口隐藏期间 Wails 事件仍派发（WebView 不销毁），done 到达时状态能复位；
  但用户重新打开窗口的瞬间若任务恰好在跑，初始渲染需依赖 GetRestoreState 兜底。

## 需求 2：导入恢复插件先无条件添加（激活），启动不兼容再自动禁用

**现状（已核实）**：`mergePluginConfigIntoProfile`（exportimport.go L554-604）当前语义是
"合并源禁用记录（目标原因优先）+ 合并 bundles 时**跳过禁用名单**"——即源机已禁用的插件
恢复后保持禁用、不激活。`finishPluginImport` 已有自愈链路：恢复后启动健康校验失败 →
`disableBootSuspects` 禁用启动日志点名插件 → 保留导入（note 提示「已恢复导入，但以下插件
与当前版本不兼容，已自动禁用…」）→ 仍失败才整体回退。**后半段已满足要求，需要改的是前半段：
恢复时不再跳过禁用、先无条件激活。**

**步骤**
1. `mergePluginConfigIntoProfile` 语义反转（exportimport.go）：
   - **不再**合并 `cfg.Disabled`、**不再**按禁用名单跳过 bundles；
   - 对被恢复的插件（`cfg.Bundles` 覆盖的名字，以及 `cfg.Dependencies` 中非官方包名）
     **无条件追加进 `dsh.profile.bundles`**（去重；bundleBase 归一处理 name@ver 变体）；
   - 同时**清除目标 profile 中这些名字的 `disabledPlugins` 条目**——激活与记录必须成对，
     否则关于页会显示「已禁用」徽标但插件实际已激活（`buildPluginRows` 只看记录不看 bundles）。
2. `exportPlugins.Disabled` 字段保留序列化（旧导出包兼容、信息不丢），恢复侧忽略即可；
   旧包无该字段自然兼容（optional）。
3. 启动失败自愈链路无需改动：`finishPluginImport` 现有 `disableBootSuspects` 会在健康校验
   失败时禁用真正不兼容的插件（写入当前环境相关的新原因），note 已走 `import:done(note)`
   展示。建议微调文案结尾补一句「插件修复后可在关于页点击『启用』」，给用户行动路径。
4. 回退兜底不变：禁用后仍失败（核心故障 / 无嫌疑）→ `rollbackImportProfiles` 整体回退，
   `.importbak` 快照会把目标机器原 package.json（含其原有禁用记录）完整还原——无损。
5. 测试更新（plugin_disable_test.go）：
   - `TestMergeSkipsDisabledBundles` 改为新语义断言：恢复插件无条件激活、
     目标原有禁用记录对被恢复名字被清除、未恢复的其它禁用记录保留、`cfg.Disabled` 不再合并；
   - 新增：目标已有禁用记录 + 恢复包覆盖该插件 → 激活且记录清除；
   - `finishPluginImport` 的自愈分支依赖真实服务启动，单测无法覆盖——真机 e2e 验证
     （旧插件 fixture vs 新核心：恢复 → 启动失败 → 自动禁用 → note 提示）。

**关键问题点**
- **记录与激活一致性**：清除 disabledPlugins 条目必须与追加 bundles 同步、按 bundleBase 归一；
  漏清会出现「徽标已禁用但实际已启用」的假状态，误导用户点「启用」。
- **作用范围界定**：无条件添加只作用于**被恢复的插件**（包内 cfg.Bundles/Dependencies 覆盖的
  名字）；目标机器上不在包内的其它禁用插件保持禁用，不能被顺带激活。
- **目标机器原有禁用原因被覆盖**：这是本需求语义的必然（恢复=重试激活）；
  若最终整体回退，目标原状态由 `.importbak` 还原，无损失；若成功且仍不兼容，插件会被
  重新禁用并写入**当前环境相关的新原因**（优于保留源机旧原因）。
- **不得在合并阶段"预判"禁用**：用户明确要求先添加、启动时不兼容再禁用；
  基于版本/来源的静态预检不可靠，以启动日志点名（`parseBootLogSuspects`）为唯一判据。
- **多插件不兼容**：沿用 `disableBootSuspects` 单轮"全部禁用嫌疑"策略，不逐一分诊；
  最终 note 必须列出全部被自动禁用的插件。
- **取舍待确认**：源机从未激活（从未入 bundles）但依赖存在过的插件，本次也会被激活
  ——按"无条件添加"字面执行；如希望保守（只激活 cfg.Bundles 覆盖的名字），实施时二选一，
  需用户拍板（默认按字面：Dependencies ∩ 非官方 全部激活）。
- 交互顺序不变：解压 → 注册合并（新语义）→ 本地链接消毒 → pnpm 对齐（含摘除重试）→
  拉起健康校验 → 失败自愈禁用 → 仍失败整体回退。恢复期间的取消机制（上一轮）不受影响。

## 验证

- 单测：merge 新语义 + 回归（禁用/启用往返、sanitize 联动等），`go test -count=1 ./...` 全绿。
- 真机 e2e（另机/换端口，3080 是会话宿主）：① 取消按钮在长恢复（大 zip）中点击后保持禁用
  直到完成；② 导出包含「旧版不兼容插件 + 已禁用插件」→ 恢复 → 全部先激活 → 启动失败 →
  不兼容者自动禁用 → 提示列出；核心无嫌疑时仍整体回退。
- 构建：`wails generate module`（如新增 GetRestoreState 绑定）+ `build.ps1 -Version v0.7.1`，不提交。
