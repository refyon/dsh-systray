## v0.10.8

自 v0.10.7 起（新增「自建 GitHub 中转 Worker」支持：私有仓插件更新也走 Cloudflare 边缘）：

### 新增

- **`mirrorBase` 配置项**：填入自建中转 Worker 的基址（如 `https://dsh-mirror.example.com`）后：
  - **下载全走中转**：自更新包、GitHub CLI、字体、版本查询一律先走 `<base>/gh/`，直连与第三方镜像仍作为回退保留（镜像链顺序：`<base>/gh/` → 显式 updateMirror → 直连 → 第三方镜像，端点重复时去重）；
  - **私有仓插件**（`github:` 来源）的安装与更新改用 `<base>/p/<owner>/<repo>/tar.gz/<commit>`：用 GitHub API 解析该仓库默认分支（或 spec 里的 `#ref`）的**最新提交**，钉成不可变地址（便于 Worker 侧缓存、结果可复现）；解析失败（无凭据 / 网络异常 / 仓库不可见）自动回退原生 `pnpm update`，不影响原有能力；
  - **凭据自动补齐**：为该 host 追加 `//<host>/:tokenHelper=<gh-token 包装器>`，与 codeload 同一套机制（token 仍由 gh 从系统凭据库读出、不落盘），pnpm 10 / 11 均生效；
  - 插件来源分类识别中转 tarball 地址为 **github 来源且可更新**，不会显示成「以固定压缩包地址安装，无法判断更新」。
- **收益（本机国内网络实测）**：同一 5.1MB 资产，GitHub 直连 0.1–0.4 Mbps、第三方镜像约 2.9 Mbps、自建 Worker（R2 命中）**9–12 Mbps**；私有仓原先走 codeload 直连约 0.2 Mbps。

### 测试

- 新增 5 例：中转地址组装/解析（拒绝非配置 host、拒绝分支名这类可变地址）、未配置 `mirrorBase` 时不改写、来源分类、`github:` spec 解析、镜像链顺序——其中「直连候选不得被误删」一条正是回归测试抓出的首版实现缺陷；
- **端到端（真实私有仓，pnpm 10.34.5 与 11.7.0 双版本）**：仅凭 npmrc 授权（不带任何显式请求头）执行 `pnpm add https://<mirror>/p/refyon/<私有仓>/tar.gz/<sha>` 安装成功；
- 全量 `go test -count=1 ./...` 绿。

## v0.10.7

自 v0.10.6 起（修复「装过私有仓插件的机器上，托盘自带 pnpm 10.34.5 之后什么包都装不动」）：

### 修复

- **codeload 凭据写法会让 pnpm 10.34.5 全面失败**（2026-09-25 源码级实证）：
  - **现场形态**：托盘为私有仓插件写入的 `~/.npmrc` 行是 `<gh.exe> auth token --hostname github.com`（带参数）。pnpm 10.34.5（首次运行时装进便携运行时的版本）的 `loadToken` 要求该值必须是「**存在的绝对路径、不带参数**」，否则抛 `ERR_PNPM_BAD_TOKEN_HELPER_PATH`——而它在每次 pnpm 启动时都会解析并加载全部 tokenHelper，所以**不只私有仓，连 `pnpm install` 公共包都跑不动**（本机实测：旧格式 exit=1，新格式 exit=0）。
  - **为何长期潜伏**：pnpm 11 的 `parseTokenHelper` 会把值按空白切成「命令 + 参数」，带参写法在它上面恰好能用——开发机走的是系统 pnpm 11，于是问题只在装有托盘便携运行时（10.34.5）的机器上出现，且表现为「什么都装不动」而非「私有仓装不上」。
  - **现在**：改为写**包装器脚本的裸路径**——在 gh 同目录生成 `gh-token.cmd`（Windows）/ `gh-token.sh`（其它平台，带可执行位），脚本内部再带参数调 `gh auth token`。pnpm 10 用 `spawnSync(值, {shell:true})` 执行、pnpm 11 对 `.cmd/.bat` 显式 `shell:true`，两个版本都接受裸路径。**token 仍只由 gh 从系统凭据库读出、不落盘**（包装器内容不含凭据），手动在终端跑 pnpm 同样受益（配置仍是用户级）。
  - **启动自愈**：启动时后台重写该行（把历史带参数旧格式迁移为新格式）；本机没有 gh 时直接**删除旧行**——它会让 pnpm 10.34.5 下所有 pnpm 操作失败，留着一定是坏事。已受影响的机器升级后无需任何操作即恢复。
  - 保留既有可表达性校验：包装器路径含空白或 `$ % ` ` " '` 时拒绝写入并告警（不写坏 npmrc、不留半成品脚本）。

### 测试

- 新增 2 例、改写 3 例既有用例：包装器脚本内容与可执行位、tokenHelper 值必须是**不含空白的裸路径**、旧格式行迁移与清理（保留其它 host 的 tokenHelper、其它配置与 CRLF 风格）、拒绝路径时不动 npmrc 且不留半成品；
- **真实回归**（两个 pnpm 版本 + 真实私有仓，非模拟）：
  - 包装器按 pnpm 的执行方式（shell）运行 → 输出真实 token（`gho_…`，40 字符）；
  - **pnpm 10.34.5**：公共包安装 **exit=1 → exit=0**（`BAD_TOKEN_HELPER_PATH` 消失）、`pnpm add github:refyon/<私有仓> --ignore-scripts` **下载成功**（证明 token 确实流到 codeload）；
  - **pnpm 11.7.0**：两项同样通过（无回归）；
  - 全量 `go test -count=1 ./...` 绿。

## v0.10.6

自 v0.10.5 起（更新与重启全面提速，实测：5.1MB 更新包 **3 分 22 秒 → 15.1 秒**、harness 更新后重启 **97 秒 → ~45 秒**、重置后重启 **99 秒 → ~15 秒**）：

### 更新提速

- **依赖安装源改为镜像优先**：`installRegistry()` 从「官方可达则官方」改为 **npmmirror 优先**（本机实测 8 并发 310 Mbps / 元数据 ttfb 43-87ms，官方 14 Mbps / 0.5-2.1s），镜像不可达才回退官方。插件与 profile 依赖安装的大头是逐包元数据与 tarball，这一段此前一直走慢源。
- **刚发布的版本仍走官方**：新增 `harnessRegistryForVersion`，按目标版本在镜像上的可见性选源——镜像已同步用镜像、镜像滞后（版本刚发布几分钟内）自动切官方，既拿到速度又不让镜像同步延迟把更新挡死（避免 `ERR_PNPM_NO_MATCHING_VERSION`）。插件「检查更新」改为官方与镜像**并行查询后选优**：版本号高者胜（保新鲜度），同版本取镜像（保速度）。
- **pnpm 环境变量双前缀写入**：实测 pnpm 10.34.5 只认 `npm_config_*`、pnpm 11.7.0 只认 `pnpm_config_*`——旧实现只写前者，导致在 pnpm ≥ 11 上 registry / fetch-retries / child-concurrency 等配置**全部静默失效**。现同一键同时写两个前缀（键名用下划线，连字符写法两个版本都不认）。
- **离线优先**：`pnpmTunedEnv` 增加 `prefer_offline`，harness 更新后逐 profile 的依赖对齐不再重取整树元数据；harness 目录的 pnpm 命令也带上安装源与离线偏好（git 等命令不注入）。
- **自更新下载改分段并发**：`downloadOnce` 改为「128KB Range 探测 → 整文件均分 4/8 段并发下载」；源忽略 Range 时直接用该响应顺序写入（不多发一次请求）；段长不符按失败处理，防截断文件被当成更新包。同时**禁用下载客户端的 HTTP/2**：镜像支持 h2 时多个 Range 请求会在同一条 TCP 连接上多路复用，等于又回到单连接限速（实测 4 段仅 1.1 Mbps，改用 4 条 HTTP/1.1 连接后 4.1 Mbps）。

### 重启提速

- **健康校验提前通过**：改为「命中就绪标志（`dsh web: http://…`，出现时插件已全部注册）+ 3 秒静默期」即判通过，原窗口（普通重启 10s / 改版后 60s）退化为上限。本机日志实证：就绪后 87 秒内没有任何 `[server]` 输出，却一直干等到窗口结束。加载错误标记仍**立即判失败**；拿不到就绪标志时行为与旧版完全一致（安全降级）。
- **迟到的加载错误转后台兜底**：提前通过后仍在后台观察到原窗口结束，真出现迟到错误（本机曾出现就绪后 45s 才刷出的 `plugin tree failed to load`）就走既有 `tryBootRollback` 自愈（先禁用肇事插件、必要时回退 LKG）并弹窗提示；有其它 harness 操作在跑时让位，避免与更新/重置/插件批处理并发地 kill/重启互相踩踏。**冷启动且存在 LKG 时不提前通过**——该路径通过后立即清 LKG，等满窗口才能保证迟到的错误仍处于可回退状态。
- **备份删除改异步**：`clearAllLkg` 与重置收尾的 `.reset-bak` 删除移到后台（新增 `removeAllAsync`，并以 `lkgFsMu` 串行化 LKG 备份目录操作，防异步删与提升/恢复竞争），LKG 标记文件仍同步清除。本机实测同步删除整棵 `node_modules` 备份要 27 秒，这部分此后不阻塞收尾提示。

### 测试

- 新增 16 例：分段下载（Range 生效 / 源忽略 Range 回退 / 段截断判失败 / Content-Range 解析）、registry 选优（官方与镜像并行结果择优）、pnpm 环境变量双前缀与替换语义、健康校验（提前通过 / 错误快速失败 / 就绪后错误仍失败 / 无标志等满窗口 / 冷启动关闭提前通过）、LKG 异步清理；
- 全量 `go test -count=1 ./...` 绿。

## v0.10.5

自 v0.10.4 起（修复「托盘外重装的插件补报不上去、反而被旧删除墓碑反复入队」，以及 0.10.4 构建脚本引入的编码缺陷）：

### 修复

- **删除墓碑已被更晚的本机安装盖过时，不再挡住对账补报**（2026-09-24 现场：重装 dsh-cost-meter 后账号记录始终停在 remove 墓碑，插件补报恒为 0）：
  - **现场形态**：删除记录（服务器 `seq=30`，17:28:55）曾被应用过，本机 17:39:09 又在托盘外把插件装了回来。`accountKeyTargetSatisfied` 对 `plugin:` 的删除目标只看「本机是否装着」、不看时间，于是这条墓碑每轮被拉取与漂移重判重新塞进「待生效」集合；而对账的数据源又会跳过所有待生效 key —— 那条本该救场的「服务器删除记录比本机安装更早 → 补报 install」规则永远执行不到。实测表现：插件补报恒为 0、待生效恒为 1 项、游标每轮回拨到 29，且点「重启生效」会把刚装好的插件再删一次，循环不收敛。
  - **现在**：删除目标增加时间判据——**本机装着但安装时间晚于该记录的写入时间时视为已满足**（墓碑已被更晚的安装盖过，不再进待生效集合）；安装更早（真正由别的设备删除）或时间未知时保守按未满足处理，行为与旧版一致。判据与对账 `accountReconcileLocalPlugins` 完全同口径，时间以服务器 `updatedAt` 为权威。
  - `account.json` 新增 `updatedAt` 字段并贯穿拉取合并、漂移重判、待生效集合与应用标记；**后向兼容**——旧记录读到 0 走保守分支，下一次拉到该记录即自动补齐并自愈，不需要手工改状态文件。
- **托盘内安装也上报 `install`**：`reportPluginBatchChanges` 此前只上报 `update` / `remove`，托盘内重装没有自己的上报通道、只能等对账兜底；而对账一旦被待生效集合挡住就永远补不上去。现在 `install` 一并上报（版本取安装结果，缺失时回退目标版本）。
- **构建脚本 `scripts/build.ps1` 的双 BOM**（0.10.4 引入）：文件开头误写成两个 UTF-8 BOM，PowerShell 只剥掉一个，残留的零宽字符让 `param(` 块无法解析——终端会打印 `# : The term … is not recognized` 与 `param : The term … is not recognized`，而脚本其余部分仍逐行执行，于是「看起来构建成功」但参数绑定失效：`-X main.appVersion=` 被注入空串，且无法再传 `-Version`。现已改为只写一个 BOM（保持仓库 .ps1 的编码约定与 LF 行尾）。

### 测试

- 新增 3 例：删除目标的时间戳判据单测（本机更新 / 本机更早 / 时间未知三分支）、卡住现场的端到端回归（待生效集合清空 + 对账补报 install 并落入上报队列）、反向保护（本机安装更早时墓碑仍保留、不补报）；
- `TestReportPluginBatchChangesFilters` 增加 install 任务与字段断言，锁住托盘内 install 上报；
- **反向验证**：临时回滚修复后前两例转红，报错即现场形态（「被更晚安装盖过的墓碑不应留在待生效集合」），确认用例确实覆盖该缺陷；
- 全量 `go test -count=1 ./...` 绿。

## v0.10.4

自 v0.10.3 起（托盘起不来时不再毫无反应，日志也不再「时有时无」）：

### 新增

- **托盘注册失败不再静默**：托盘窗口 / 图标 / 菜单初始化失败时经 `systray.SetOnFail` 弹窗告知具体原因与日志路径后退出（Windows 与 macOS 同构）。本程序没有主窗口，此前失败只写一行日志，用户看到的是「双击没反应」，也无从判断是没启动还是启动后崩了。
- **启动首行记录执行上下文**：`dsh-systray vX starting (pid=…), log file: …, integrity=<High/Medium/Low> session=<n> user=<SID>`。托盘注册返回 `Access is denied` 时可直接比对「起得来的那次」与「起不来的那次」是否处在不同完整性级别 / 会话（Windows 实测：进程完整性会被镜像文件的强制标签封顶，低完整性进程的托盘注册被任务栏按 UIPI 拒绝）。
- **`DSH_SYSTRAY_LOG_DIR` 环境变量**：显式覆盖统一日志目录（诊断与特殊部署用）。

### 修复

- **统一日志落盘自愈，不再「时有时无」**：打开主日志失败时按「修权限位 → 给日志目录打低完整性可写标签 → 旧文件改名让位并保留现场」自愈后重试，全部失败才回退系统临时目录，并把失败原因写进启动日志与 stderr——此前回退到 Temp 后日志页（读主目录）看不到本次启动，表现为「日志时有时无」。
- **构建产物可直接运行**：`scripts/build.ps1` 编译后把 `src\build\bin` 与产物 exe 的强制完整性标签置为 High。仓库位于 agent 工作区时整棵树带 `Low` 标签，Windows 会用镜像标签给进程完整性封顶，产物只能以低完整性启动、托盘注册被任务栏拒绝（`Access is denied` 闪退）。标签设置失败只告警不中断，并明确提示产物将以低完整性运行。

### 测试

- 全量 `go test -count=1 ./...` 绿。

## v0.10.3

自 v0.10.2 起（修复「启动时显示已同步、手点「立即同步」才弹出「重启生效」」）：

### 修复

- **启动后状态行误报「已同步」**：状态行只看 `lastSyncedAt`——那是**上一会话**留下的时间戳，而本次会话的启动检查要等 20 秒才做。这段时间里界面显示绿色「已同步」，服务器上却可能已有本机没拉到的记录，于是必须手点「立即同步」才会弹出「重启生效」。现在：
  - **启动即检查**：首次同步检查的等待从 20 秒缩短到 5 秒（该检查只读本机文件 + 一次网络请求，与服务启动无依赖）；
  - **「尚未检查」与「已同步」分开**：新增 `startupChecked` 状态，本会话检查完成前显示「正在检查同步…」（左侧导航小字同步显示「正在检查同步…」），检查完成后才按真实结果渲染「已同步 / 待生效 N 项 / 同步失败」；
  - 检查**成功或失败都算已检查**（失败走「同步失败：原因」分支，不会卡在「正在检查同步…」）；手动「立即同步」成功同样置位——启动检查前手点同步，状态行立刻按本次结果渲染；
  - 登出 / 换账号复位该标记。

### 测试

- 新增用例：启动载入时为「未检查」（即使带着上一会话的 `lastSyncedAt`）、首次后台检查后置位、检查失败同样置位且带失败原因、启动检查就把服务器记录变成待生效（不需手点同步）、手动同步成功置位、登出复位；
- 反向验证：临时去掉置位调用后前三个用例全部转红；

## v0.9.1

自 v0.9.0 起（私有仓库插件在本机跑不通的两处根因 + 更新步骤的拉包凭据补齐 + 插件「启用」并入批量操作）：

### 修复

- **网络瞬断时授权流程把 API 端点当授权页打开**：设备码请求被阻断时（2026-09-14 本机实证：21s 连接超时，同时段 `git pull` 也是 21s 超时），`gh` 打印的是 Go 的 `*url.Error`——`Post "https://github.com/login/device/code": …`。旧逻辑按「github.com 域名」判定授权页，取到的正是这个 **API 端点**、且一次性授权码解析为空（日志实证 `opening https://github.com/login/device/code": (code length=0)`）：浏览器打开了 API 页面、用户无从填码，整条授权流程停在死路上。现只认设备授权页本身（`github.com/login/device`），并一并修剪行尾引号等标点；gh 升级提示里的 release 链接同样不再被误当授权页。
- **起流失败自动重试**：拿到授权码之前失败不再一次收尾——用户此时还没拿到任何东西，自动重试最多 3 次（间隔 2s），进度窗口显示「正在重新连接 GitHub（第 N/3 次尝试）…」；授权码/地址一旦已展示给用户就不再重试（重试会换一个新码，让用户手里的码失效）。
- **授权失败不再只留一句「仓库不可见」**：失败原因（gh 的原话）写入统一日志的 ui 模块，日志页可直接看出授权卡在哪一步；此前只有成功路径写日志。
- **镜像 404 不再被当成「仓库不可见」**：只有直连 GitHub 官方端点（唯一携带凭据的通道）的 404/403 才算「仓库对当前身份不可见」；镜像不转发凭据，其 404 只说明通道失败。此前直连被间歇阻断时，会把**已授权**的用户反复推回授权，却始终失败。

### 新增

- **私有仓库插件的「更新」补齐拉包凭据**：检查更新只用内存 token，但更新（`pnpm` 重解析并下载私有仓库）还要两个凭据出口——`git ls-remote` 解析引用（本机实证：未认证 `could not read Username`）与 `codeload.github.com` 拉 tarball（本机实证：未认证 404）：
  - 授权成功后自动执行 `gh auth setup-git`：git 配置里只写「凭据助手命令」，token 仍由 gh 从系统凭据库读取；
  - 在**用户级** `~/.npmrc` 写入 `//codeload.github.com/:tokenHelper=<gh> auth token --hostname github.com`（pnpm 执行该命令、取 stdout 作 token，配置里同样没有 token）。pnpm 明确拒绝项目级 `.npmrc` 的 tokenHelper，故必须写用户级；写入幂等、只动这一行、原子替换，保留用户既有配置。
  - 升级到本版本前**已完成授权**的机器不会重走授权流程，因此在执行 github 来源插件更新前也会幂等补配一次。
  - `gh` 路径含空白或 pnpm 保留字符（`$ % ` `"` `'`）时跳过并写告警日志（tokenHelper 无法表达这类路径，检查更新与授权不受影响）。
- **插件「启用」并入批量操作**：点「启用」此前是立即执行（停服 → 加回启用清单 → 重启校验），与「更新 / 删除」的「先登记、后应用」批处理不一致——两个启用同时点会互相 kill 服务、抢 3080 端口（2026-09-12 本机实证：一次把无辜插件误判为「仍不兼容」并重新禁用）。现 `pluginOpTask.op` 新增 `enable`：
  - 登记只接受「已禁用且仍有依赖声明」的行（无依赖的自动禁用记录提示直接删除，未禁用行拒绝）；
  - 执行阶段只改 profile 声明（清禁用记录 + 加回激活清单）：**无 pnpm、不搬 node_modules**，快照只备份声明文件，回退不触发重装；
  - 与更新 / 删除共用同一个待应用区与**批末唯一一次**启动校验——统一处理完只重启一次服务；仍不兼容时由既有两级自愈自动重新禁用（原因取启动日志）并在汇总里如实报告；
  - 启用成功即提升 LKG，否则冷启动回退会拼出「旧启用清单 + 当前禁用态」的不一致组合。

## v0.9.0

自 v0.8.13 起（私有仓库插件的 GitHub 授权、插件删除前的会话数据风险检查）：

### 新增

- **私有仓库插件的 GitHub 设备流授权**：插件装在私有仓库时，「检查更新」此前只能报「仓库不可见」——未认证访问私有仓库必然 404，用户没有任何完成授权的入口。现补齐整条链路：
  - **授权引导**：检查更新报「仓库不可见」时弹出自绘确认框（「登录 GitHub」/「取消」），不再使用 Wails 的 `MessageDialog`——它在 Windows 上只是 `MessageBoxW(MB_YESNO)`，**忽略自定义按钮**，自定义按钮永远不会出现。
  - **GitHub CLI 自动就位**：首次授权若本机没有 `gh`，自动下载并解包官方便携版（约 15 MB），下载接入与 harness 更新同一个进度窗口；下载失败即复位状态，重试不必重启程序（慢网不再被单次总超时打断，改为「停滞看门狗 + 换镜像 + 整轮重试」）。
  - **一次性代码显示在窗口里**：`gh` 在非终端环境不会自己拉起浏览器，只打印设备授权页地址；现由 dsh-systray 打开浏览器，并把**一次性授权码直接显示在进度窗口**（同时写入系统剪贴板），用户可以直接照抄或粘贴。
  - **凭据不进 systray**：token 由 `gh` 写入系统凭据库（Windows 凭据管理器 / macOS 钥匙串），程序只在内存中短暂持有，不落盘、不写日志，也**只对 GitHub 官方域名**携带凭据，第三方镜像不转发。
- **托盘「设置」不再打断进行中的进度**：设置窗口已经打开时，「设置」只把窗口带到前台，不再重载内容——此前重载会把正在进行的进度界面（更新下载 / 授权 / 导入恢复）整块换成设置页，用户既看不到进度也看不到「取消」入口。窗口未打开时仍按正常启动加载并刷新版本与插件清单。

### 修复

- **导入恢复期间重新添加压缩包导致状态错位**：恢复进行中重新选择压缩包会把导入项状态整体复位，而后端仍按旧包内容执行。现前后端双层拦截（按钮置灰 + 后端拒绝且不改动已解析的导入项）。
- **取消恢复后立刻重新恢复会被拒**：取消受理后行内过早解锁，用户秒点「恢复」会撞上「该恢复项已在处理中」（旧任务还在回退、尚未出队）。现取消后保持占用直到真正收尾，兜底计时到点先向后端确认再决定是否解锁；入队被拒也不再显示成「恢复失败」。
- **多次取消后一直停在「恢复中」**：队列里「已发布结果的残留条目」既不会被取消也不会出队，每次取消都命中它却永远等不到结果。现这类条目直接退休出队；另外修掉一个真正的丢唤醒——worker 排空队列后进入批末收尾期间新入队的任务不会被任何 worker 执行（现场日志：整批只处理了 1 个任务，而第二次「恢复」已被受理）。
- 恢复各阶段（暂停服务 / 覆盖拷贝 / 依赖安装 / 回退 / 批末收尾 / worker 退出）写入日志，这类队列问题不再只能靠猜。

### 变更

- **删除插件前先查「会话数据风险」**：插件可以往会话日志里写入自己的事件类型，若它没有按 harness 的外部插件约定给这些事件标 `ignorable: true`，卸载后 harness 读日志会 fail-closed——「类型未知且未标 ignorable」即拒绝解析整份日志，Web UI 报「历史加载失败」，这些会话再也打不开（2026-09-13 实证：dsh-cost-meter 写入的 `cost-meter/native-search-usage`；`dsh-session-persistence` 的读路径按白名单校验，写路径不校验，所以插件能写进去、删掉插件后就打不开了）。
  - **登记删除时自动检查**：按事件命名空间归因插件包名（`cost-meter/native-search-usage` ↔ `dsh-cost-meter`），只认该插件写入且未标 ignorable 的事件。有风险时插件行显示警示「删除后 N 个历史会话将无法打开（该插件写入了 M 条自定义记录）」，关于页待生效提示同步追加数量。**只提示、不阻断**：登记照旧一步完成、不弹确认框；风险信息随 `config.json` 跨托盘重启保留。
  - **一键「修复会话」**：给这些事件补上 `ignorable: true`（harness 为「可安全跳过的外部事件」提供的正式兼容标记，计费/统计类记录正属此列）。修复只动会话日志——不停服、不重启；按帧重压缩且只改受影响帧，原日志逐个备份为 `*.bak-<时间戳>`，修复后立即复查并回报残留（插件仍在运行时可能继续写入，可再修复一次）。
  - 检查范围只含当前世代日志（`session.v<N>.jsonl[.zstd]`）：版本 0 的旧世代沿用无版本文件名，其事件词表属历史格式、由 harness 的迁移路径处理，不纳入本检查（否则会把旧格式误判成这次删除带来的风险）。会话日志是拼接的多帧 zstd，扫描与修复走 Node 一次性脚本（与插件入口预检同一形态），不新增 Go 依赖；Node 过旧（不支持 zstd，需 22.15+ / 24+）时脚本会点名原因并按失败归因，不静默跳过检查。

- **删除后重新导入的插件仍显示「已删除」**：行内结论（已删除 / 已更新 vX / 有新版本）此前只按插件名缓存，删除生效时写入的「已删除」会在插件被重新导入、行重新出现后原样贴回。现给行内结论加「产生时版本」戳（删除类记空版本——只有该行不存在时才成立），版本再次变化即自动过期；并在插件导入完成时整体清空行内缓存后重载，重新导入的插件不再残留旧状态。

### 新增

- **插件变更改为「先登记、后应用」（不再点一下就重启服务）**：点击插件的「更新」/「删除」只登记变更——**不弹确认框**（登记不执行、可随时撤销，确认纯属多余）、不停服、不切走窗口，行内显示「待应用：…（重启服务后生效）」并给出「撤销」。
  - **关闭设置窗口时询问**：「有 N 项插件变更尚未应用（更新/删除需要重启后台服务才能生效），是否现在应用并重启服务？」选「立即应用并重启」即刻执行（进度窗口收尾时自动隐藏窗口）；选「稍后」则照常隐藏，变更留在待应用区。
  - **关于页待生效提示（只报数量，不列条目）**：存在未应用变更时，插件卡片顶部显示单行提示「有 N 项变更尚未生效（X 项更新 · Y 项删除）重启服务后生效」，右侧固定「全部撤销」（带二次确认）与「立即应用」；不渲染条目列表以免挤占卡片高度，逐条的「待应用」状态与「撤销」按钮仍在下方各插件行内。跨托盘重启保留（写入 `config.json`，启动时逐条校验，插件已被移除等失效条目自动丢弃）。
  - **一次重启完成全部变更**：应用时整批只停一次服务、逐项独立快照执行包操作，全部完成后统一做一次启动校验（此前每项操作各自停服 + 各自跑 ≥10s 健康校验窗口，N 项插件就是 N 次重启）。单项 pnpm 失败只回退该项（其余继续），批末校验失败才走自愈（禁用启动日志点名的嫌疑插件 → 兜底禁用全部已激活用户插件），仍失败才整批逆序回退。
  - 更新前处于「已禁用」的插件：应用时随本批解除禁用，由同一次启动校验判定——仍不兼容则自动重新禁用，不额外增加重启次数。
  - 「待重指定」「无依赖的自动禁用」行仍走记录清理，不触发停服与重启。
  - **按最后操作生效**：同一插件重复登记时同操作幂等、换操作覆盖（先登记删除、又登记更新 → 以更新为准）；应用前按当前插件状态重新校验，插件已不存在则跳过该项。
  - **重新导入即最后一次操作**：导入恢复成功后，本次恢复覆盖到的插件其先前登记的更新/删除一律作废，并在导入结果中说明（典型：先登记删除、随后又把它导回来，则不再删除）。
  - 互斥：harness 更新/重置进行中拒绝登记插件变更；应用进行中拒绝新登记与更新/重置 harness——两者都会停服并跑 pnpm。

## v0.8.3

自 v0.8.2 起（三项改进：mac 本地插件重选仍未加载续查、日志页完整显示、禁用优先于版本回退）：

### 修复

- **mac 重选本地插件后仍未加载（R2 定案）**：待重指定插件重选目录时，若历史记录 bundled=false（源机未激活），重选事务只清记录、不把插件加回激活清单——spec 与 node_modules 均已就位但 harness 从未加载它，且无任何提示。现在**重选 = 显式激活**：无论历史 bundled 真假，重选一律补进 `dsh.profile.bundles`。
- **mac 旧服务进程不退出导致新配置永不加载**：`killServer` 对端口监听进程只发一次 SIGTERM；旧进程未退出时重启校验误判「端口已有可用服务」而跳过重启，插件重选/更新/导入的新配置不生效。现 SIGTERM 后轮询端口释放，仍存活时 SIGKILL 兜底（与 Windows taskkill /F 语义对齐）。
- **日志页内容不完整（三处丢失点）**：前端 4000 行 DOM 裁剪把最早写入的行静默丢弃；日志轮转后 offset 跳到新文件末尾，把「轮转后新写入的行」整体跳过（mac 每次服务重启都轮转）；轮转归档 .1/.2/.3 不参与展示，轮转前的历史从页面消失。现在日志页 = 归档（旧→新）+ 基础文件完整拼接，检测到轮转自动清空视图重载，清空日志一并删除归档。

### 变更

- **禁用优先、回退兜底**：更新 harness / 导入插件后服务启动失败时，先按启动日志点名禁用肇事插件；未奏效或无点名嫌疑时禁用全部已激活的用户插件再试，仍失败才回退版本。冷启动失败同样先尝试「禁用肇事插件保留当前版本」，都失败才恢复 LKG 旧版本。禁用只摘除激活清单并记录原因，可在关于页逐个重新启用。
- 本地插件重选/更新成功弹窗：所选目录缺少 node_modules（依赖未安装/未构建）时附排查提示；终态日志逐 profile 输出并记录 node_modules 链接状态。

### 移除

- 日志页 DOM 行数裁剪（与「完整显示所有已写入内容」冲突）。

## v0.8.2

自 v0.8.1 起（mac 用户实证：导入的本地插件重选目录后仍不加载、日志页空白）：

### 修复

- **mac 本地插件重选后不加载（dsh-ui-taste 实证）**：待重指定插件重选目录时，若所选目录版本与 node_modules 残留副本一致，前端把「版本相同」误判为「无需操作」而跳过执行（只提示「已经是最新版本」），pending 记录 / bundles 激活 / link: spec 从未修复 → 插件永不加载。现在待重指定行任何目录选择都走「重新指定」确认并执行完整重链接事务（清待重指定 + 恢复激活 + 改写来源 + 安装 + 重启校验）。

- 本地插件重选/更新成功后在日志记录一行终态快照（依赖 spec、bundles 激活、待重指定、禁用状态），便于此类问题凭日志一次定案。

### 移除
